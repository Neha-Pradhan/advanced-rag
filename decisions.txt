D13 · Chunking rule (baseline)
Section-aware on NCERT "N.N Title" headings = base unit. Sections within 256-token
budget → 1 chunk. Oversized sections → sub-split on SENTENCE BOUNDARIES (never
mid-sentence) with small token overlap; heading prepended to every sub-chunk.
Token budget measured with MiniLM's own tokenizer (tokens, not words/chars);
real text budget = 256 − heading tokens − safety margin.
Why sentence-boundary over hard-cut: mid-sentence cuts smear the chunk embedding
(harder to retrieve the right chunk) and can fracture a fact across chunks. Effect
is a quality nudge not correctness-critical, but cheap to do right at this scale.
Rejected: LLM-summarize-long-chunks (throws away detail RAG needs) — parked as
small-to-big / parent-doc candidate for Phase 6.

D14 · Two transports over one retrieval core
Core: src/retrieve.py stays a plain Python module (search + grade filter + gate).
Transport 1 — Streamlit app for the student: keeps control of the answer layer
(grade-appropriate phrasing, consent fallback, figure display) rather than handing
generation to a general-purpose assistant. Also avoids putting an open-ended chatbot
in front of a 12-year-old during study time.
Transport 2 — MCP server: learning chapter only (MCP is a flagged gap; Crisil JD
lists it). Tested with MCP Inspector (free, official) or a VS Code MCP client —
no Claude Desktop / paid plan needed. Server is client-agnostic by protocol design.
Why both: wrapper changes, core doesn't. Story: "retrieval core, two transports."

D15 · Chunking: library splitter + post-process, not hand-rolled
Use LangChain's RecursiveCharacterTextSplitter (token-length fn = MiniLM tokenizer)
for sub-splitting oversized sections, not hand-rolled sentence logic. Re-inject

Supersedes original "no frameworks at first" for THIS component. Learning preserved

P9 · Retrieval score bands (MiniLM, real measurement)
In-corpus query "what is a cell made of": top hit 0.549, all top-5 ≥ 0.49, all from
the correct section (2.1). Out-of-corpus "who won the cricket world cup": top hit
0.247, sliding to 0.18, hits are unrelated science chunks (nearest ≠ relevant).
Key: MiniLM relevant hits live in 0.4-0.6, NOT 0.8+. A naive 0.7 threshold would
reject every good hit. Threshold must be calibrated to THIS model. Clean gap here
(~0.5 vs ~0.25) but science-adjacent-but-absent queries would score mid-range and
fool a pure threshold → why the 2nd-stage LLM relevance check exists.

GATE vs RAGAS (don't conflate)
LLM relevance gate = RUNTIME component. Per user query, post-retrieval: cheap LLM
asks "do these chunks answer this question?" → "no" triggers consent fallback.
Ships to production, runs on every query, invisible to user.
RAGAS = OFFLINE eval framework. Run during development over a test Q&A set to MEASURE
retrieval/answer quality (faithfulness, answer relevancy, context precision). Grades
the system; not part of it. Run per-experiment (e.g. before/after swapping a model).
Gate = runtime behavior. RAGAS = measuring tape. No overlap.

P10 · Gate two-stage: which stage earns its keep (open question)
Measured: cricket 0.25 (reject S1), black holes 0.32 (reject S1), cell 0.55 (pass),
moon phases 0.770 (pass — highest score seen, near-exact topic match). Score bands
wider than first thought (0.25 → 0.77). In ALL test queries so far, stage-1 score
floor alone decided correctly; stage-2 LLM check only ever confirmed a pass — hasn't
yet caught anything stage 1 missed. Stage 2's real job = high-score-but-irrelevant
(vocabulary overlap inflates score, e.g. a named entity present but question
unanswerable). Not yet demonstrated on a real query. Revisit: find a query that
passes S1 but should fail, to prove S2 earns its place (or drop it if it never does).

P11 · Resilient batch API pattern (learned via 503)
Gemini free tier throws transient 503s. Robust batch-of-LLM-calls needs THREE things
together: (1) retry with exponential backoff (1,2,4,8s, bounded → fails fast, never
hangs), (2) resume — skip already-done items on re-run, (3) incremental save — write
after EACH item, not just at end. Resume + end-only-save = half a fix (nothing to
resume from after a mid-run crash). Incremental save + resume = crash-proof.

D23 · Model swap: 3.6-flash → 2.5-flash-lite (rate limits)
gemini-3.6-flash is a PREVIEW model with a stingy free cap (~20 req/day) — hit it
during eval-reference generation. Swapped to gemini-2.5-flash-lite: stable (non-
preview), flash-lite class = highest free daily quota (~1000-1500 RPD), fast + cheap,
ample for answer-gen + RAGAS judging + student's daily use. Lesson: newest ≠ best on
free tier; preview models have tighter limits than mature ones. Centralized
GEMINI_MODEL in config → one-line swap.
